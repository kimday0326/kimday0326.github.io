웹 성능을 이야기할 때 빠지지 않는 주제가 바로 **Head-of-Line (HOL) Blocking**입니다. HTTP 버전이 올라가면서 많은 것이 개선됐지만, HOL Blocking은 HTTP/2에서도 완전히 사라지지 않았습니다. 이 글에서는 HOL Blocking이 어디서 비롯되는지, 각 버전이 어떻게 대응했는지, 그리고 왜 HTTP/3에서야 비로소 TCP 레벨의 문제가 해결됐는지를 살펴봅니다.

---

## Head-of-Line Blocking이란

HOL Blocking은 **앞선 요청 하나가 막히면 뒤의 요청들이 모두 대기하게 되는 현상**입니다. 식당에서 앞 테이블 손님이 주문을 결정하지 못해 뒤에 줄 선 모든 손님이 기다리는 상황과 같습니다.

네트워크에서는 이 문제가 두 레이어에서 발생합니다.

- **HTTP 레이어**: 요청/응답의 처리 순서 제약
- **TCP 레이어**: 패킷 유실 시 재전송 대기

두 레이어의 차이를 이해하는 것이 HTTP 버전별 개선 내용을 파악하는 핵심입니다.

---

## HTTP/1.1의 HOL Blocking

### 하나의 커넥션, 하나의 요청

HTTP/1.0에서는 요청마다 TCP 연결을 새로 맺었습니다. HTTP/1.1은 `Connection: keep-alive`를 기본값으로 도입해 연결을 재사용할 수 있게 했지만, 한 연결에서는 여전히 **요청→응답→요청→응답** 순서를 반드시 지켜야 했습니다.

```
클라이언트                       서버
   |                              |
   |--- GET /index.html -------->|
   |<-- 200 OK (HTML) -----------|
   |--- GET /style.css -------->|   ← index.html 응답이 끝나야 보낼 수 있음
   |<-- 200 OK (CSS) ------------|
   |--- GET /app.js ----------->|
   |<-- 200 OK (JS) ------------|
```

`/style.css` 응답이 느리면 그 뒤의 모든 요청이 기다립니다. 이것이 HTTP/1.1의 HOL Blocking입니다.

### 파이프라이닝: 반쪽짜리 해결책

HTTP/1.1은 **파이프라이닝(Pipelining)** 을 스펙에 포함했습니다. 응답을 기다리지 않고 여러 요청을 한꺼번에 보내는 방식입니다.

```
클라이언트                       서버
   |                              |
   |--- GET /index.html -------->|
   |--- GET /style.css -------->|  ← 응답 안 기다리고 연속 전송
   |--- GET /app.js ----------->|
   |                              |
   |<-- 200 OK (HTML) -----------|
   |<-- 200 OK (CSS) ------------|  ← 반드시 요청 순서대로 응답
   |<-- 200 OK (JS) ------------|
```

문제는 응답도 **요청 순서대로** 반환해야 한다는 규칙입니다. `/style.css` 응답이 느리면 이미 완성된 `/app.js` 응답도 그 뒤에 줄을 서야 합니다. HOL Blocking이 완전히 해소되지 않습니다.

실제로 파이프라이닝은 프록시 호환성 문제와 구현 복잡성 때문에 Chrome, Firefox 모두 기본 비활성화했고, 사실상 사용되지 않는 기능이 되었습니다.

![HTTP/1.1 파이프라이닝과 HOL Blocking 개념도](https://images.unsplash.com/photo-1544197150-b99a580bb7a8?w=800&h=400&fit=crop)

### 현장에서 쓰던 회피책들

파이프라이닝이 현실적으로 동작하지 않자, 개발자들은 다른 방법을 찾았습니다.

**도메인 샤딩(Domain Sharding)**

브라우저는 호스트당 병렬 TCP 연결 수를 제한(보통 6개)합니다. `static1.example.com`, `static2.example.com` 처럼 서브도메인을 여러 개 만들면 더 많은 병렬 연결을 확보할 수 있습니다.

```html
<!-- 도메인 샤딩 예시 -->
<link rel="stylesheet" href="https://static1.example.com/style.css">
<script src="https://static2.example.com/app.js"></script>
<img src="https://static3.example.com/hero.png">
```

DNS 조회와 TCP 핸드셰이크 비용이 늘어나는 단점이 있었습니다.

**스프라이트 이미지(CSS Sprite)**

여러 아이콘을 하나의 이미지로 합쳐 요청 수 자체를 줄이는 방식입니다.

**번들링과 인라이닝**

JS·CSS 파일을 하나로 합치거나 HTML에 직접 인라인하여 요청 수를 최소화했습니다.

| 기법 | 해결 방법 | 부작용 |
|------|----------|--------|
| 도메인 샤딩 | 병렬 연결 수 증가 | DNS 조회, TLS 핸드셰이크 오버헤드 |
| 스프라이트 | 요청 수 감소 | 이미지 관리 복잡성 |
| 번들링 | 요청 수 감소 | 캐시 효율 저하, 초기 로드 무거움 |
| 인라이닝 | 요청 수 감소 | 캐시 불가, HTML 비대화 |

이 기법들은 모두 HOL Blocking을 근본적으로 해결하는 게 아니라 **요청 수를 줄이거나 병렬성을 인위적으로 높여 증상을 완화**하는 접근입니다.

## HTTP/2: 멀티플렉싱으로 HTTP 레이어 해결

### 스트림과 멀티플렉싱

HTTP/2의 핵심은 **멀티플렉싱(Multiplexing)** 입니다. 하나의 TCP 연결 위에 여러 **스트림(Stream)** 을 열어, 요청과 응답을 독립적으로 주고받습니다.

```
클라이언트                       서버
   |                              |
   |=== Stream 1: GET /index ===>|
   |=== Stream 2: GET /style ===>|  ← 동시에 전송
   |=== Stream 3: GET /app.js ==>|
   |                              |
   |<=== Stream 2: 200 CSS =======|  ← 완성된 순서대로 응답 가능
   |<=== Stream 3: 200 JS ========|
   |<=== Stream 1: 200 HTML ======|
```

응답이 완성되는 순서대로 돌아올 수 있습니다. HTTP/1.1에서 필요했던 도메인 샤딩, 스프라이트, 과도한 번들링은 HTTP/2 환경에서는 오히려 역효과를 낼 수 있습니다.

![HTTP/2 멀티플렉싱 다이어그램](https://images.unsplash.com/photo-1451187580459-43490279c0fa?w=800&h=400&fit=crop)

### HTTP/2가 가져온 것들

멀티플렉싱 외에도 HTTP/2는 성능에 영향을 주는 여러 기능을 도입했습니다.

- **헤더 압축(HPACK)**: 반복되는 HTTP 헤더를 압축해 전송
- **서버 푸시(Server Push)**: 클라이언트 요청 전에 서버가 리소스를 미리 전송
- **스트림 우선순위(Priority)**: 중요한 리소스를 먼저 처리하도록 힌트 제공

### 그럼에도 남은 문제: TCP HOL Blocking

HTTP/2는 HTTP 레이어의 HOL Blocking을 해결했지만, **TCP 레이어**의 HOL Blocking은 여전히 남아 있습니다.

TCP는 데이터를 **패킷 단위**로 전송하고, 패킷이 손실되면 재전송을 요청합니다. 그리고 **손실된 패킷이 도착할 때까지 이후 패킷 처리를 중단**합니다. 이것이 TCP의 순서 보장 메커니즘입니다.

```
TCP 수신 버퍼
+--------+--------+--------+--------+--------+
| Pkt 1  | Pkt 2  | [유실] | Pkt 4  | Pkt 5  |
+--------+--------+--------+--------+--------+
                     ↑
              Pkt 3 재전송 대기 중
              → Pkt 4, 5는 도착했지만
                상위 레이어로 전달 불가
```

HTTP/2에서 여러 스트림이 하나의 TCP 연결을 공유하기 때문에, **패킷 하나가 유실되면 무관한 스트림들도 모두 멈춥니다.**

역설적으로 HTTP/1.1에서는 여러 TCP 연결을 열어서 한 연결의 패킷 유실이 다른 연결에 영향을 주지 않았습니다. HTTP/2의 단일 연결 아키텍처가 TCP HOL Blocking에는 더 취약한 면이 있습니다.

네트워크 품질이 좋은 환경에서는 HTTP/2가 항상 빠르지만, **패킷 손실률이 높은 불안정한 네트워크(모바일, 저품질 Wi-Fi)에서는 HTTP/1.1보다 느려질 수 있다**는 연구 결과도 있습니다.

## HTTP/3와 QUIC: 전송 레이어부터 바꾸다

### TCP를 버리고 UDP 위에 새 프로토콜을

HTTP/3는 TCP 대신 **QUIC(Quick UDP Internet Connections)** 을 전송 레이어로 사용합니다. QUIC는 UDP 위에서 동작하지만, TCP가 제공하는 신뢰성(재전송), 흐름 제어, 혼잡 제어를 직접 구현합니다.

핵심 차이는 **스트림 단위로 신뢰성을 보장**한다는 점입니다.

```
QUIC 스트림 독립성

Stream A: [A1][A2][A3 유실][A4][A5]
                  ↑
            A3 재전송 대기 → Stream A만 영향

Stream B: [B1][B2][B3][B4][B5]  ← 정상 진행
Stream C: [C1][C2][C3][C4][C5]  ← 정상 진행
```

Stream A의 패킷이 유실되어도 Stream B, C는 계속 데이터를 전달받습니다. TCP HOL Blocking이 구조적으로 발생하지 않습니다.

![QUIC 스트림 독립성](https://images.unsplash.com/photo-1558494949-ef010cbdcc31?w=800&h=400&fit=crop)

### 연결 설정 비용 절감

QUIC는 연결 수립 과정도 크게 개선했습니다.

| | TCP + TLS 1.2 | TCP + TLS 1.3 | QUIC (HTTP/3) |
|--|--------------|--------------|--------------|
| 최초 연결 | 3-RTT | 2-RTT | 1-RTT |
| 재연결 | 2-RTT | 1-RTT | 0-RTT |

QUIC는 TLS 1.3을 내장하여 암호화 핸드셰이크와 전송 핸드셰이크를 한 번에 처리합니다. 이전에 연결했던 서버라면 저장된 세션 정보로 **0-RTT** 연결도 가능합니다.

### Connection Migration

모바일 환경에서 Wi-Fi에서 LTE로 전환되면 IP 주소가 바뀝니다. TCP는 IP+포트 조합으로 연결을 식별하기 때문에 네트워크가 바뀌면 연결이 끊어집니다.

QUIC는 **Connection ID**로 연결을 식별하므로 IP가 바뀌어도 연결이 유지됩니다. 모바일 사용자 경험이 크게 개선되는 부분입니다.

## 정리: 각 버전이 해결한 것과 남긴 것

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|--|---------|--------|--------|
| HTTP HOL Blocking | ❌ 존재 | ✅ 해결 | ✅ 해결 |
| TCP HOL Blocking | △ 다중 연결로 완화 | ❌ 더 심화 | ✅ 해결 (QUIC) |
| 연결 수립 비용 | 높음 | 낮음 | 매우 낮음 |
| 헤더 압축 | ❌ | ✅ HPACK | ✅ QPACK |
| 네트워크 전환 | ❌ 연결 끊김 | ❌ 연결 끊김 | ✅ Connection Migration |

HTTP의 발전은 단순히 기능 추가가 아니라, **병목이 어느 레이어에 있는지를 파악하고 그 레이어를 공략하는 방식**으로 이루어졌습니다. HTTP/1.1은 애플리케이션 레이어 회피책에 의존했고, HTTP/2는 HTTP 레이어를 고쳤으며, HTTP/3는 전송 레이어 자체를 교체했습니다.

## 마치며

HOL Blocking은 단일한 문제가 아닙니다. HTTP 레이어와 TCP 레이어에서 각각 다른 원인으로 발생합니다. 이 사실을 모르면 "HTTP/2로 업그레이드했는데 왜 느리지?" 같은 상황에서 원인을 찾기 어렵습니다.

실제 서비스에서는 여전히 HTTP/1.1과 HTTP/2가 혼재하고, HTTP/3 지원도 환경마다 다릅니다. 어떤 버전을 쓰든 그 버전의 특성을 이해하고 최적화 전략을 선택하는 것이 중요합니다.

> HTTP/2 환경에서 도메인 샤딩을 쓰거나 HTTP/1.1 환경에서 파일을 쪼개지 않고 무거운 번들로 묶는 것은 모두 프로토콜 특성을 오해한 데서 비롯된 실수입니다.

각 프로토콜이 무엇을 해결하고 무엇을 남겼는지 알면, 성능 최적화 결정을 더 근거 있게 내릴 수 있습니다.
